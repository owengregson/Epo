# Cursor motion QC — 2026-09-21

The pointer now uses WindMouse-style forces: attraction toward the target,
correlated wind, momentum, and a damped final approach. The previous path used a
quadratic Bézier curve with a mostly fixed number of samples for each distance.
The new implementation varies trajectory geometry, sample count, and timing,
while enforcing exact endpoints and bounded per-event velocity.

These are measured properties of the generated plans. They do not establish
that the output matches a population of human users or defeats platform
detection. The comparison does not open Instagram or send any page input.

## Reproduce the measurements

From the repository root, using the installed dependencies:

```sh
node scripts/motion-qc.mjs \
  --baseline-ref 864f6bad78ef3b8f15343255bdc4310d8cae9da3 \
  --samples 500 \
  --out /tmp/epo-motion-qc-2026-09-21.json

npx jest tests/interaction/motion-profile.test.ts tests/interaction/windmouse.test.ts --runInBand
```

The script prints JSON and optionally saves it to `--out`. Without
`--baseline-ref`, it compares the working tree against `HEAD`. Pin the commit
above to reproduce this report after these changes are committed. The script
loads the baseline and any of its motion dependencies from the same Git tree;
it does not mix old code with current dependencies.

Each case uses seeds 0–499, start point `(100, 300)`, a horizontal destination,
and the stated target width in CSS pixels. Both versions receive the same
seed sequence. The previous implementation consumes random values differently,
so this compares distributions, not matched individual trajectories. The
baseline uses its original `pathBetween`, `travelDurationMs`, and `stepDelays`
composition. The current implementation uses `movementPlan`, the production
Interactor's motion-planning entry point. The report includes the commit IDs,
current-source SHA-256 hashes, Node/runtime, sample count, timestamp, duration
percentiles, unique paths and cadences,
event counts, speed limits, and full current distribution summaries.

## Results

500/500 plans reached the exact destination in every case, for both versions.
The 2,400 CSS px/s threshold is the new declared policy ceiling, not a measured
human population limit.

| Distance / target width | Previous peak px/s | Current peak px/s | Previous events above ceiling | Current | Distinct event counts, previous → current |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 / 40 px | 1,062 | 807 | 0 | 0 | 1 → 15 |
| 700 / 40 px | 4,837 | 2,026 | 1,833 | 0 | 4 → 54 |
| 2,000 / 40 px | 11,257 | 2,395 | 16,925 | 0 | 4 → 121 |
| 2,000 / 1,000 px | 45,028 | 2,395 | 22,391 | 0 | 4 → 118 |

The large-target case exposed the most consequential defect: a short Fitts-style
duration could be applied to a long trajectory without checking individual
segment velocities. Current timing expands the duration when necessary to
respect the velocity and minimum event-delay constraints.

For the 700 px / 40 px target case:

- All 500 paths and all 500 timing sequences were distinct.
- Duration p10 / median / p90: **608 / 730 / 872 ms**.
- Emitted event-count p10 / median / p90: **49 / 60 / 76**.
- Median path length was **1.043×** the straight-line distance; maximum **1.193×**.
- Median speed during the final three steps was **11.6%** of mid-flight speed.
- **97/500** plans included an explicit bounded overshoot and correction.
- Peak lateral deviation had a median of **49.4 px**.

The old integer rounding accumulated up to 9 ms of total-duration error across
these cases. Current timing apportions integer delays to the exact feasible
budget; when the requested duration conflicts with event-delay or velocity
floors, the feasible budget intentionally increases. A separate regression
checks exact apportionment rather than inferring it from endpoint timing.

Boundary timing also exposed an avoidable repetition pattern: for a 1 px move
and 40 px target, **471/500** old duration draws were exactly 120 ms. The new
bounded distribution reduces that to **6/500**, increases distinct durations
from **14 to 76**, and has a 144 ms median. A separate 30,000 px synthetic stress
case reduced draws pinned at the 1,400 ms ceiling from **392/500 to 0/500**.
That stress case tests the duration sampler only; the complete plan still
extends its duration as needed to honor the per-event speed limit.

## Correctness coverage

The focused suites passed **37 tests** when this report was created. The new
trajectory invariant test spans **768** seeded combinations of six distances
and four directions and checks more than **20,000** individual segments.
It checks finite coordinates, exact endpoints, nonzero segments, maximum step
length, delay floors, and per-segment velocity ceilings.

Additional checks cover:

- Viewport-edge trajectories, including overshoot clamped at an edge, without
  duplicate endpoint events.
- Degenerate random sources returning 0, 0.5, or 1; integration remains bounded
  and converges.
- NaN/infinite coordinates, invalid target widths, and excessive distances.
- Zero-distance moves producing no duplicate event or artificial wait.
- Longer movements and smaller targets taking longer in aggregate.
- Very short and duration-capped moves retaining timing variation instead of
  concentrating their draws at exactly 120 ms or 1,400 ms.
- Click points sampled within a target's visible intersection with the viewport;
  completely offscreen controls are rejected.
- Subpixel target rectangles and removal of the old probability pileups at
  clamped click margins.
- Tiny nonzero scroll requests producing nonzero wheel events.

Viewport bounds are an input to the motion planner. A production caller must
obtain the actual CSS viewport, intersect partially visible controls with it,
clamp a cursor position made stale by resizing, and abort a pending trajectory
when the viewport dimensions change. Electron view bounds alone are insufficient
when page zoom changes the relationship between DIP and CSS pixels. These
integration conditions are separate from the pure-plan measurements above.

## Source and implementation choices

The primary model reference is Ben Land's
[WindMouse explanation](https://ben.land/post/2021/04/25/windmouse-human-mouse-movement/),
which describes attraction, smoothly varying random wind, velocity constraints,
and damping near the destination. The author explicitly labels the published
reference implementation GPLv3. That code and the existing `sliced.sh`
implementation were inspected for comparison; neither was copied or imported.

`src/interaction/windmouse.ts` is an independent implementation of that force
model with continuous distance-based braking, a bounded trajectory corridor,
optional viewport constraints, and an explicit bounded convergence tail. Its
timing allocation is separate from its geometry. All tunable gains and limits
live in `src/kernel/motion-policy.ts` and are labelled policy choices, not
fabricated empirical measurements. The repository's license is unchanged and
no third-party implementation was vendored.

Observed browser dispatch timing, operating-system scheduling, minimized-window
survival, and input confirmation require the separate real Electron input
probe. The offline evidence here does not replace those checks.
