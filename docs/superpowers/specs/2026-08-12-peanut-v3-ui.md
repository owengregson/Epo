# Peanut v3 — Dashboard UI Design (Fable-authored)

**Date:** 2026-08-12 · **Author:** Fable (design). Implementation delegated to Opus against this spec.
**Depends on:** Wave 4 (the `Foundation`/Engine IPC surface + `EngineStatus`).

---

## 1. Aesthetic direction — "instrument panel," not "app"

Linear/ChatGPT-minimal, but with the specific character the product owner asked for: **monotone
graphite greys with whitish-silver / brushed-metal accents and a restrained shiny flair.** The feel is
a precision instrument watching a live process — calm, dense, legible — not a colorful consumer app.

- **No** violet/glassmorphism, no gradients-as-decoration, no emoji, no drop-shadow soup.
- Palette (tokens on `:root`, theme-aware; this is a desktop Electron app so dark is primary):
  - `--bg #0d0d0f`, `--surface #141417`, `--elevated #1b1b1f`, `--border #26262b`, `--border-strong #33333a`.
  - Text `--text #ececee`, `--muted #9a9aa2`, `--faint #66666e`.
  - Metal accents (use sparingly — hairlines, active states, the running pulse): a cool silver
    `--silver #c9ccd1` and a brighter edge `--chrome #eef1f4`; a single functional accent for "live/go"
    `--live #d8dde3` (near-white steel), and semantic `--warn #d8b768` (muted brass), `--danger #c96a6a`.
  - The only "shine": 1px top highlight on raised surfaces (`inset 0 1px 0 rgba(255,255,255,.04)`) and a
    subtle brushed-metal sheen on the primary control (a very low-contrast linear-gradient on the
    Start/Stop button and the status pill). Nothing glows.
- Type: system stack (SF Pro / Inter / system-ui); tabular-nums for all counters; 12–13px dense body,
  one 15px panel title tier. Generous hairline dividers, tight vertical rhythm.

## 2. Layout

The existing split stays: **dashboard on the left (fixed ~460–520px), the live embedded Instagram
`WebContentsView` on the right.** The dashboard is a single scrolling column of stacked panels with a
persistent top **control bar**. The user watches the app act on the right while the left narrates.

```
┌──────────────────────────┬───────────────────────────────┐
│ CONTROL BAR (sticky)      │                               │
│  ● state · Start/Pause/Stop                               │
├──────────────────────────┤        Instagram tab          │
│ CHAIN panel               │      (WebContentsView)        │
│ RATE / SAFETY panel       │                               │
│ QUEUE panel (tabs)        │                               │
│ ACTIVITY LOG panel        │                               │
│ SETTINGS (collapsible)    │                               │
└──────────────────────────┴───────────────────────────────┘
```

## 3. Panels & the data each binds to

All live fields come from `EngineStatus` (pushed via the existing `on('status')` channel + a
`status()` pull on mount). List data needs a few **new read-only IPC handlers** (see §5).

- **Control bar** — a state pill (`idle/running/paused/halted`, colorized: running = steel `--live`
  with a slow 2s pulse, halted = `--danger`, paused = `--warn`); Start / Pause·Resume / Stop buttons
  (metal-sheen primary); a `dryRun` indicator when on. Halts show `lastSentinel`/halt reason inline in
  `--danger`.
- **Chain panel** — the self-chaining story: `currentTargetUsername` (+ `chainIndex`), and the target
  lineage from `chain:list` (each with source badge seed/discovered/own-followers and its yield:
  follow-back rate, pool size). This is the product's signature view — make the current target
  prominent, the lineage a compact vertical trail beneath.
- **Rate / Safety panel** — `actionsToday / dailyOperatingRate` as a slim meter, `remainingToday`,
  `atHardCeiling` (turns the meter `--danger` at the ceiling), `requestBudgetRemaining` as a second
  thin meter, active-hours state, and `nextActionAt` (derive an ETA from `lastActionAt` + delay, or
  show "waiting"). These are the ban-safety vitals — always visible, never alarming unless real.
- **Queue panel (tabbed)** — real `follow_records` grouped by lifecycle state via `queue:list`:
  **Queued** (`queued`), **Awaiting follow-back** (`pending_followback`), **Held** (`followed_back`,
  show `holdUntil`), **Due to unfollow** (`unfollow_queued`). Each row: avatar-less username, ratio,
  private badge, and the relevant timestamp. Counts come from `EngineStatus` (`queued`,
  `pendingFollowback`, `followedBackHeld`, `unfollowDue`); rows are lazy-loaded per tab (cap ~100,
  note truncation). NO index arithmetic — bind to real state (the old versions' bug).
- **Activity log** — the streamed structured logger (already piped to the renderer). Monospace, newest
  at bottom, auto-scroll with a pause-on-scroll-up, level filter chips (debug/info/warn/error) that
  actually work (the level is configurable now). Scrubbed of nothing — usernames are fine locally.
- **Settings (collapsible)** — the `Settings` object (§4 of the engine arch). Grouped: Targeting
  (seed, ratio band+peak, size band, private boost), Lifecycle (wait/hold/retries), Safety (hard
  ceiling, operating rate, delays, jitter, active hours, request budget), Cadence (sweep, plan size,
  low-water), Dry-run. **Live validation** as you type: yellow above the operating-rate guidance, red
  approaching the hard ceiling; the hard ceiling input is capped in the control and the engine enforces
  it regardless. Save writes via `settings:update` (persist + reload the engine's derived configs).

## 4. Interaction & correctness rules

- **Push-first, no fighting poll:** subscribe to `status`; do a single `status()` on mount; do NOT run
  a competing interval that overwrites fresh pushes (the old renderer's flicker bug). A slow 10s
  keep-alive pull is fine only as a fallback if no push arrived.
- **Every async control shows pending/disabled state** and surfaces typed failures as an inline toast
  (in-VDOM, not imperative DOM). No operation reports success on failure.
- **Listener hygiene:** all `on(...)` subscriptions are torn down via `off(...)` on unmount (the preload
  already supports exact-listener removal).
- **Empty/again states:** every panel has a designed empty state ("No target yet — set a seed and press
  Start"), and a not-logged-in state (prompt to log in in the right-hand tab).

## 5. New read-only IPC the UI needs (add to Foundation + preload)

- `chain:list → Target[]` with per-target yield (`store.listTargets` + `store.targetYield(pk, ownPk)`).
- `queue:list(state) → Array<{pk, username, ratio, isPrivate, followedAt?, holdUntil?, unfollowDueAt?}>`
  (from `store.followRecordsByState` joined to `store.getAccount`).
- `settings:get → Settings`, `settings:update(partial) → Settings`.
- (Logs already stream via `on('log')`.)
These are pure store reads; keep them behind `Foundation` (store single-boundary preserved).

## 6. Component structure (Preact, matches existing renderer)

`App.tsx` (shell + status subscription + view state) → `ControlBar`, `ChainPanel`, `RatePanel`,
`QueuePanel` (+ `QueueTab`), `ActivityLog`, `SettingsPanel`. A tiny `useEngineStatus()` hook (subscribe
+ pull + teardown) and a `useToasts()` hook. One `tokens.css` for the palette + a `app.css` for layout.
Keep components small and focused; no component owns more than its panel's state.

## 7. Scope discipline

This is a control surface for a working engine, not a CRM. Build the seven panels above and nothing
more. The embedded IG tab does the heavy visual lifting (the user literally sees the follows happen);
the dashboard's job is to make the invisible state (chain, safety budget, lifecycle queues) legible.
